# Taste
- Expects the implementation to be read and understood before any edit; asks explicitly to "inspect the existing implementation before changing anything" and repeats this per subsystem (handlers, cleaners, schedulers). Confidence: 0.9
- Preserves existing behaviour by default — scoring, eligibility rules, caps, ordering, exclusions and configuration — and expects changes to be strictly limited to what was requested. Confidence: 0.85
- Prefers reusing what already exists (existing locks, helper functions, existing logging style, existing selection logic) over introducing a second implementation or a new framework. Confidence: 0.8
- Favours incremental per-item work with expensive library-wide work deferred to a separate scheduled/manual reconciliation pass, rather than doing global work after every item. Confidence: 0.75
- Wants filtering/narrowing pushed as far down the pipeline as safely possible (into the query/DB) instead of computing everything and filtering just before the write. Confidence: 0.7
- Dislikes redundant writes: if the computed desired state equals the current state, nothing should be written to the external system. Confidence: 0.7
- Prefers explicit, typed identification over name/path-pattern heuristics for destructive operations, and being conservative — delete nothing — when ownership cannot be positively proven. Confidence: 0.7
- Asks for timing/performance instrumentation around hot code paths, using the project's existing logging conventions rather than a new logging framework. Confidence: 0.7
- Writes long, numbered specs (primary goal, current problem, per-section requirements, "do not change" constraints) and expects them followed section by section. Confidence: 0.65
- Before a behaviour change, wants the whole data flow traced end to end (every source, cache, normaliser, fallback and downstream consumer) and explicit questions answered — "do not modify scoring until the matching path is understood". Confidence: 0.75
- Wants one central classification/normalisation authority reused by every source, rather than each source getting its own competing rule set ("reuse existing classification rather than creating competing rules"). Confidence: 0.75
- Prefers exact matching first, then a deliberately narrow fallback, and never merging results obtained by different strategies (no summing tiers). Confidence: 0.65
- Under genuine uncertainty prefers the conservative answer — keep things separate / do nothing — over a plausible but unproven positive match. Confidence: 0.7
- Wants per-decision provenance logged (what was requested, what matched, which strategy matched) so a future bad match is obvious, at DEBUG rather than flooding INFO. Confidence: 0.7
- Expects a structured closing report: root cause, files changed, what old vs new behaviour is, tests added, test results, and questionable cases deliberately left unchanged. Confidence: 0.65
- Expects responses to be delivered in full and flags it when output is cut off mid-sentence ("You cut off the result at the end"); completeness matters more than brevity for analysis reports. Confidence: 0.6
- Reports regressions as a terse symptom of user-visible output ("the artist playlist no longer contains X", "the queue doesn't seem to be working too often", "its still showing Santana cover"), often dumping raw runtime log lines instead of pointing at a file or cause, and expects the agent to trace the root cause itself and fix it without being asked for a plan first — including a symptom that survived an earlier fix, where the ask is to trace the whole flow for every remaining cause rather than patch the reported spot, and a different track regressing right after a fix landed for another one ("that fixed that one, but X is now showing as…"), where the previous fix is suspect and must be made correct without breaking the cases it had already got right. Confidence: 0.85
- Refuses to relieve a saturation/backlog symptom by raising capacity ("I would not increase max_in_flight yet. That could simply create more stuck entries"): the blocked reconciliation path must be made to work first, with any worker-count increase only after the root cause is fixed. Confidence: 0.6
- Prefers broad, canonical categories over fine-grained ones when generating or naming outputs — group and label by main genres/families (Rock, Pop, Punk, Metal) with subgenres folded into their parent, never split or named after a subgenre — while still exposing which categories are included as a configurable option. Confidence: 0.7
- Judges genre merging by real-world taxonomy, not by name similarity: two spellings of the SAME genre are one genre ("punk" + "punk rock" must share one canonical id and one playlist), but two genres that merely share a name root and live in DIFFERENT families must stay separate — "Hardcore Punk and Hardcore are different genres. Hardcore Punk is Punk, Hardcore is Metal" — and folding one into the other (an alias making metal Hardcore resolve to the punk genre) is reported as the bug. Confidence: 0.75
- Expects closely related identities (hardcore / metalcore, alternative metal / alternative rock, ancestor/child genres) to collapse to one label on a single track rather than being listed side by side. Confidence: 0.6
- Wants reports/exports to state how fresh their underlying data is (e.g. a last-scanned timestamp) so stale numbers are distinguishable from current ones. Confidence: 0.55
- Expects the app's own annotations to outrank metadata-provider values: a track already flagged as a cover keeps its "(X Cover)" title suffix when the provider offers the same clean title, and only a later cover-detection scan may remove it if the verdict was wrong. Confidence: 0.6
- Defines track identity by TRACK ARTIST + title, not by album artist or album: for compilations ("Various Artists") and cross-album cases, a match is valid as long as the track artist and song name agree, with the album treated as context rather than part of the identity; when a release-level identity is missing entirely (a VA compilation that was never an official release), the artist-name + track-name pair must still be used rather than the track being skipped. Confidence: 0.75
- Prefers reusing audio already in the collection over acquiring it again (e.g. copy the file from another album into the downloads folder and re-import it instead of fetching it), but insists such a shortcut obey exactly the same gates as a real download — quality/format rules and track-length tolerance — rather than being a shortcut around validation. Confidence: 0.65
- Expects a full scan's fetched metadata to be persisted, so a later compare/review does not re-propose corrections (e.g. genres) that the scan should already have applied; re-surfacing the same suggested edit after a completed scan is reported as a bug. Confidence: 0.75
- Wants the scan-versus-review split to obey the "update during scan" config literally: when applying is enabled the scan writes the fetched value, when it is not the existing value is left untouched and the change is offered only as a suggestion — a scan that silently keeps a stale value is as wrong as one that overwrites a curated one. Confidence: 0.65
- Prefers lookup/search features to query every provider by default and surface all candidates as a pickable list, instead of silently auto-selecting one "best" result the user cannot compare or override. Confidence: 0.6
- Prefers a search/lookup flow to attempt the query automatically with the values already at hand (the current track's artist and title) rather than demanding the user type them, while keeping those values editable inside the same dialog with its own search button so a miss can be corrected and retried without closing it — a no-result state must never be a dead end. Confidence: 0.6
- Wants selection dialogs to list what the app already has first (e.g. albums already in the download queue) above the free-text search, so an existing or previously-missed record can be picked without searching for it again. Confidence: 0.6
- Distinguishes Various Artists compilations from single-artist compilations (greatest hits / covers albums): guards and absolute thresholds intended for VA releases must be scoped to VA only, never applied to an artist's own compilation ("that compilation guard is only meant to be for Various Artist compilations, not artist compilations"). Confidence: 0.65
- Wants missing metadata resolved automatically by the background scan pipeline rather than behind a manual button the user must click — when a manual lookup already works, the ask is to move that capability into the automatic pass so no manual action is needed. Confidence: 0.6
- Probes metric/score semantics before changing behaviour — asks point-blank comparison questions ("is X better than Y?", "is X actually used for this cutoff?") and expects a direct recommendation grounded in the real code paths, including which key is safer for which purpose and any discrepancy/bug found along the way, rather than a change made silently. Confidence: 0.55
- Judges aggregated genre/metadata output by cross-source consensus: a tag that only one provider supports while several providers agree on a large, coherent cluster is "completely wrong" and should be cancelled out in favour of the majority ("alt rock is completely wrong based on the other genres, so should be cancelled out due to the rest"). Confidence: 0.6
- Treats authoritative provider metadata as outranking the app's own name-pattern guesses: when MusicBrainz says a release is a plain Album, an album title that merely contains a compilation-ish word ("ANThology") being classified/persisted as a compilation is reported as a bug — a local heuristic must not override the provider verdict. Confidence: 0.6
- Wants a cover's "original artist" taken from the earliest commercial release/recording, not from writer/creator credits — creator-based lookup was picking up songwriters instead of the first commercial release, so attribution logic must stay release-date driven. Confidence: 0.55
- When several candidate editions are equally complete (same track count and track names), prefers the simplest, least-fragmented one — a digital single-disc edition over a multi-disc repackaging — while a genuinely more complete edition must still win. Confidence: 0.6
- Judges ratings relative to the artist's own catalogue, not in the absolute: an album that is weak across a large body of the artist's work should be penalised with fewer top-tier (4★/5★) tracks, while a genuine standout on that same album must still be allowed to reach 5★, and a new album that has not yet had time to gather plays must be exempt from the penalty entirely. Confidence: 0.65
- Wants agreed tuning values baked into the shipped defaults (default-config constants, config-page values/placeholders, and the JS serialisation bundles) so a fresh deployment starts from them, rather than existing only as a setting changed in the current install. Confidence: 0.55
- Expects skip/cooldown optimisations to be invalidated whenever the data a later stage depends on changes: if anything that affects the finalise pass is written (genres, popularity counts/scores, cover/live flags, release year), that album must be re-finalised on the next run instead of being skipped as "unchanged" — stale derived state is treated as a bug. Confidence: 0.65
- Insists on a specific processing ORDER when preference rules meet evidence: validate/reject weak or incompatible outliers FIRST, apply the collection's preference policy SECOND, remove redundancy LAST — so one thinly-supported tag cannot trigger a sweeping rule and dictate the result ("an isolated bad metal tag [must not] control the entire result"). Confidence: 0.7
- Rejects invented tuning values: "do not introduce arbitrary confidence percentages merely to complete the configuration" — thresholds and weights must be derived from and validated against the measured preview/regression results, and existing source ranking/weighting is retained rather than swapped for a new scoring scheme. Confidence: 0.6
- Wants the app to take a position when it surfaces several equivalent copies of something: rather than only flagging the duplication and leaving the comparison manual, it should recommend which copy to keep based on better metadata or better quality. Confidence: 0.5
- Expects the configuration/UI surface to shrink when the underlying data is fixed: asks whether a settings block is "still needed in the config page ... being that we've cleaned up" the upstream tagging, and treats a knob whose logic is now redundant (or that still reads stale source data instead of the cleaned value) as something to delete outright rather than preserve — including deleting its code path and tests, with old config keys left ignored. Confidence: 0.55

Confidence: 0.5
