# Taste
- Expects the implementation to be read and understood before any edit; asks explicitly to "inspect the existing implementation before changing anything" and repeats this per subsystem (handlers, cleaners, schedulers). Confidence: 0.9
- Preserves existing behaviour by default — scoring, eligibility rules, caps, ordering, exclusions and configuration — and expects changes to be strictly limited to what was requested. Confidence: 0.85
- Prefers reusing what already exists (existing locks, helper functions, existing logging style, existing selection logic) over introducing a second implementation or a new framework. Confidence: 0.8
- Favours incremental per-item work with expensive library-wide work deferred to a separate scheduled/manual reconciliation pass, rather than doing global work after every item. Confidence: 0.75
- Wants filtering/narrowing pushed as far down the pipeline as safely possible (into the query/DB) instead of computing everything and filtering just before the write. Confidence: 0.7
- Dislikes redundant writes: if the computed desired state equals the current state, nothing should be written to the external system. Confidence: 0.7
- Prefers explicit, typed identification over name/path-pattern heuristics for destructive operations, and being conservative — delete nothing — when ownership cannot be positively proven. Confidence: 0.7
- Asks for timing/performance instrumentation around hot code paths, using the project's existing logging conventions rather than a new logging framework. Confidence: 0.7
- Writes long, numbered specs (primary goal, current problem, per-section requirements, "do not change" constraints) and expects them followed section by section. Confidence: 0.65
- Before a behaviour change, wants the whole data flow traced end to end (every source, cache, normaliser, fallback and downstream consumer) and explicit questions answered — "do not modify scoring until the matching path is understood". Confidence: 0.75
- Wants one central classification/normalisation authority reused by every source, rather than each source getting its own competing rule set ("reuse existing classification rather than creating competing rules"). Confidence: 0.75
- Prefers exact matching first, then a deliberately narrow fallback, and never merging results obtained by different strategies (no summing tiers). Confidence: 0.65
- Under genuine uncertainty prefers the conservative answer — keep things separate / do nothing — over a plausible but unproven positive match. Confidence: 0.7
- Wants per-decision provenance logged (what was requested, what matched, which strategy matched) so a future bad match is obvious, at DEBUG rather than flooding INFO. Confidence: 0.7
- Expects a structured closing report: root cause, files changed, what old vs new behaviour is, tests added, test results, and questionable cases deliberately left unchanged. Confidence: 0.65
- Expects responses to be delivered in full and flags it when output is cut off mid-sentence ("You cut off the result at the end"); completeness matters more than brevity for analysis reports. Confidence: 0.6
- Reports regressions as a terse symptom of user-visible output ("the artist playlist no longer contains X", "the queue doesn't seem to be working too often"), often dumping raw runtime log lines instead of pointing at a file or cause, and expects the agent to trace the root cause itself and fix it without being asked for a plan first. Confidence: 0.7
- Prefers broad, canonical categories over fine-grained ones when generating or naming outputs — group and label by main genres/families (Rock, Pop, Punk, Metal) with subgenres folded into their parent, never split or named after a subgenre — while still exposing which categories are included as a configurable option. Confidence: 0.7
- Wants reports/exports to state how fresh their underlying data is (e.g. a last-scanned timestamp) so stale numbers are distinguishable from current ones. Confidence: 0.55
- Expects the app's own annotations to outrank metadata-provider values: a track already flagged as a cover keeps its "(X Cover)" title suffix when the provider offers the same clean title, and only a later cover-detection scan may remove it if the verdict was wrong. Confidence: 0.6
- Defines track identity by TRACK ARTIST + title, not by album artist or album: for compilations ("Various Artists") and cross-album cases, a match is valid as long as the track artist and song name agree, with the album treated as context rather than part of the identity; when a release-level identity is missing entirely (a VA compilation that was never an official release), the artist-name + track-name pair must still be used rather than the track being skipped. Confidence: 0.75
- Prefers reusing audio already in the collection over acquiring it again (e.g. copy the file from another album into the downloads folder and re-import it instead of fetching it), but insists such a shortcut obey exactly the same gates as a real download — quality/format rules and track-length tolerance — rather than being a shortcut around validation. Confidence: 0.65
- Expects a full scan's fetched metadata to be persisted, so a later compare/review does not re-propose corrections (e.g. genres) that the scan should already have applied. Confidence: 0.6
- Prefers lookup/search features to query every provider by default and surface all candidates as a pickable list, instead of silently auto-selecting one "best" result the user cannot compare or override. Confidence: 0.6
- Prefers a search/lookup flow to attempt the query automatically with the values already at hand (the current track's artist and title) rather than demanding the user type them, while keeping those values editable inside the same dialog with its own search button so a miss can be corrected and retried without closing it — a no-result state must never be a dead end. Confidence: 0.6
- Wants selection dialogs to list what the app already has first (e.g. albums already in the download queue) above the free-text search, so an existing or previously-missed record can be picked without searching for it again. Confidence: 0.6
- Distinguishes Various Artists compilations from single-artist compilations (greatest hits / covers albums): guards and absolute thresholds intended for VA releases must be scoped to VA only, never applied to an artist's own compilation ("that compilation guard is only meant to be for Various Artist compilations, not artist compilations"). Confidence: 0.65
- Probes metric/score semantics before changing behaviour — asks point-blank comparison questions ("is X better than Y?", "is X actually used for this cutoff?") and expects a direct recommendation grounded in the real code paths, including which key is safer for which purpose and any discrepancy/bug found along the way, rather than a change made silently. Confidence: 0.55
